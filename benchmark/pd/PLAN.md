# 异构双机 PD 压测

本计划以约 14K 输入的编码助手请求为主场景，并增加长短混合负载。性能矩阵与历史 vLLM/SGLang Control 成绩分开解释；可行性实验只用于确认部署方向。

## 比较对象

| 代号 | NVIDIA RTX 5070 Ti | AMD RX 7800 XT | 要回答的问题 |
| --- | --- | --- | --- |
| N | 单卡完整推理 | 空闲 | NVIDIA 单卡基线 |
| A | 空闲 | 单卡完整推理 | AMD 单卡基线 |
| NP-AD | Prefill | Decode | 已通过可行性验证的方向 |
| AP-ND | Decode | Prefill | 交换角色能否改善性能 |
| REPLICAS | 完整推理副本 | 完整推理副本 | 两卡收益是否需要 PD |

所有方案处理同一批请求。REPLICAS 每条请求只送一个副本，按最少未完成请求路由，平局轮流；它回答相同双卡资源下的部署选择，不代表最优路由策略。混合负载另列两副本实际接收的长度分布和请求数。

现有可行性证据只证明 NP-AD 可完成请求。AP-ND 尚未完成模型验证。此前长请求出现过计算语义偏离，实际缓存校验通过，差异仍未定位。

## 开跑条件

1. 验收 AP-ND：短请求、分块 Prefill、多轮消息、SSE、KV 与 GDN 状态校验；输出同时对照 N、A。交换角色时 endpoint 与 bootstrap 角色必须同时切换，不能只交换 HTTP URL。
2. 两方向都检查请求与状态槽对应关系，并发至少尝试 1/2/4 的隔离用例，排除串请求、丢状态、重试退回。长输入必须覆盖 14,336 token，固定答案分别放在输入开头、中间、末尾；再验收真实多轮和 1024-token 长生成。短输入要求可重复输出。未解释的长生成差异单列，不能宣称质量等价。若出现状态损坏、错误答案或串请求，停止正式性能比较。
3. 核对权重 revision/文件哈希、tokenizer、模板、源码与补丁。实验目标改为 **context 32,768**，冻结 FP16/AWQ、CPU 权重卸载 0 GiB、chunked prefill 256、Triton 后端；先沿用 Graph/overlap/radix cache 关闭的共同配置。单卡也使用这组配置。原有 8192 上限不能运行本轮负载。输入加输出必须在上下文内，且先通过模型配置与运行时长度检查；只改 context 参数不算容量验收。生产配置不改。
4. 校准显存容量。现有 `max-running-requests=1`、8192 token 池、5 个 Mamba 槽需要重新验收。先验证单条 14,336+1024；再逐级测并发 2/4。若要求 C 条长请求同时驻留，token 池需求粗算至少 `C×15,360`，还要加分页对齐、中间状态及角色专用缓冲，实际以启动日志和调度记录为准。32K context 是单请求上限，不等于总 token 池必须设为 32K。冻结每张卡在各角色间可复用的容量；共同可用并发进入主比较，独有容量另报。记录实际权重、KV、状态池、工作区和峰值，0.90 不代表实际资源相等。若 16 GB 显存下只有并发 1 能运行，保留该结论，混合负载测排队，不冒称多请求同时驻留；不通过缩短 14K 输入或打开权重卸载补救。
5. 正确性验收保留 checksum；计时前关闭两端诊断 checksum 和逐传输 trace，核验实际加载版本。每种形状主动预热，排除 JIT/首次分配；连续三个预热窗口延迟变化小于 10% 后计时，十个窗口仍不稳定则先排查。
6. 测双向有效带宽和 RTT：至少 1/16/64/128/**512 MiB**，每档 10 次，包含 GPU→传输→GPU 的同步完成。512 MiB 档用于覆盖 14K 请求的状态量。记录链路速度、主机 CPU/RAM 和 SSH/TUN 占用。GPU buffer 校验通过不等于吞吐已达标。
7. Windows 启动 runner 前，使用已验证的 Python 解释器；启动后核对 runner 进程仍存活，并确认执行状态文件已更新。

本轮保留当前 TUN→TCP→SSH 路径，所有成绩标注该条件。若换为直连/其他网络，整个对照重新分批，不能把换网前后的成绩拼在一起。TCP 主机缓冲不属于模型权重 CPU offload。

## 第一组：交换 P/D 方向

用 N、A、NP-AD、AP-ND 四种配置跑下表，单卡数据供第二组解释结果。1K 在本计划中指 1024 token，14K 指 14,336 token。用户曾观测 Claude Code 请求输入约 14K，本计划不把这个数当成所有 Claude Code 会话的固定开销。

长度按**最终模板化、分词后的完整输入**计数，包括 system、工具定义、messages、代码、工具返回和模板特殊 token，不能只数最后一条用户消息。长输入由脱敏的编码助手提示、工具 schema、代码片段和历史消息组成，避免用同一句话循环填充。保存精确 token ID、组成比例和 seed；同一请求在五方案中相同。主矩阵固定输出长度，temperature=0、ignore_eos=true、thinking 关闭，用于控制计算量；真实 EOS 和工具调用见后面的会话补测。

| 负载 | 输入 / 输出 token | 首要观察 | 预期及成立条件 |
| --- | --- | --- | --- |
| S：短请求 | 128 / 512 | TPOT、输出吞吐、E2E | 保留低输入开销对照，观察长 Prefill 插入时的 Decode 停顿 |
| L：长输入隔离 | 14,336 / 256 | TTFT、Prefill 时间、传输等待 | 缩短输出以突出长输入代价；更快的 Prefill 必须抵消状态传输 |
| C：编码助手 | 14,336 / 1024 | TTFT、TPOT、E2E、goodput | 主场景，比较完整长请求及排队收益，不能只看输出 token/s |

筛选：4 配置 × 3 负载 × 并发 1/2/4 = **最多 36 单元**；每单元至少 10 条且至少 30 秒。 14K/1024 预跑中，AMD 单条约 113 秒，故冻结提交预算为 S 900 秒、L 1200 秒、C 2400 秒；不足样本仍标记不完整。并发表示客户端闭环在途请求数，不能把结果叫开环容量。

正式：保留 L、C 两档负载，每档使用并发 1 和该负载四配置共同通过的最高并发 C*，始终进行 3 次独立启动重复，**最多 48 单元**。S 保留筛选结果，主要用于混合负载的短请求对照。原方案的 512/256、2048/64 降为可选历史尺度，不再扩展主矩阵。

每张卡、每个角色都记录自己的 Prefill/Decode 服务时间。跨机阶段耗时使用各自主机的单调时钟测时长，不拿两个主机的时间戳直接相减。用实测服务时间预测方向优劣，再用正式批次检验。

## 第二组：单卡与 PD

第一组的并发 1 结果用于低负载对照，预计单卡经常占优，因为 PD 增加传输和协调时间。第二组专门测长 Prefill 与正在 Decode 的请求相互干扰时，PD 能否改善尾延迟。

两种混合负载分别回答真实调用和调度干扰的问题，比例按请求条数计算：

| 轨迹 | 构成 | 用途 |
| --- | --- | --- |
| M-code：主场景 | 80% C（14,336/1024）+20% 中等请求（2048/256） | 代表编码助手多数请求都有长系统/工具上下文；进入正式测试 |
| M-interference：干扰诊断 | 80% S（128/512）+20% C（14,336/1024） | 检查少量长 Prefill 是否拖慢短请求的流式输出；先做筛选 |

各轨迹生成独立的长度排列和泊松到达时间，固定 seed，五种配置重放相同请求。10 条为一个组成块，避免小样本下混合比例失真。不得等待前一请求完成后才发下一条。保留计划到达、实际提交、首个内容、完成时间和请求类别，统计发生器排队与提交延迟。M-interference 分别报告 S/C 的 P95，不能用总体平均掩盖短请求停顿。

另做一次小规模时间线诊断：先让 S 开始 Decode，再提交 C；每方案重复 10 对，记录 C 到达前后 S 的输出 chunk 间隔、服务端调度与传输。它解释干扰来源，不作为独立请求吞吐结果，也不假定每个 chunk 恰好一个 token。

分别用独立校准数据估计 N 在两份轨迹下的可持续到达率 λN：无持续队列增长、错误率≤1%，并满足下述 SLO。各轨迹冻结四档公共速率 **0.5/0.8/1.0/1.2 × 该轨迹λN**，五种配置使用相同绝对 RPS。不同轨迹的 λN 不能混用，也不能给每个方案按自身容量归一化后直接比吞吐。

筛选：2 轨迹 × 5 配置 × 4 速率 = **40 单元**。每档至少到达 10 条且至少 60 秒，提交预算统一为 2400 秒；到达窗口结束后最多排空 120 秒。记录未完成、超时、拒绝和发生器延迟，不丢弃失败样本。

正式：M-code 预先固定 0.5λN、1.0λN 两档，5 配置 × 2 速率 × 3 次重复 = **30 单元**。M-interference 先保留筛选与时间线结果；若要正式报告其尾延迟收益，必须补同样 30 单元的三次重复，单列扩展批次。两档速率不足以精确估计最大容量，不外推容量上限。若五种配置都无压力或都排队，先修正校准并冻结新矩阵，再整组重跑。

预期：低负载暴露 PD 通信代价；混合负载接近 N 的容量时，AP-ND 若能持续供给 NVIDIA，可能降低其 Decode 停顿和 P95 TPOT。若 AMD Prefill 或传输已饱和，TTFT/排队反而上升。单卡的 chunked prefill 同样保持启用，避免人为放大单卡干扰。REPLICAS 用于判断 PD 是否比两卡独立服务更合算。

## 会话补测：冷输入与复用前缀

14K 总输入不等于每轮都重新计算 14K。主矩阵关闭 radix/prefix cache，测**冷输入成本与 PD 隔离**；不能把它直接当作真实多轮交互成绩。

补一组脱敏编码助手会话：每方案 10 个会话、每会话 3 轮，共 **150 条请求**，先做描述性验证，不计入正式矩阵。首轮完整输入为 14,336 token，后两轮追加用户消息、预录制历史回复与工具结果；各部署重放相同输入，当前回复不回填后续轮次。输入自然增长，按实际 token 数分桶。max output 1024，允许 EOS，不强制生成满额。不执行模型返回的工具命令。本批次通过 native `/generate` 回放已模板化 token ID，保存模板与工具 schema。

先以 cache 关闭跑一遍，作为必做补测；再独立验收该版本、混合模型和异构 PD 的前缀复用支持。通过后五方案全部开启可用的前缀缓存，再以同一会话轨迹跑暖缓存组，另增加 150 条。REPLICAS 采用会话粘性路由；首轮冷、后两轮暖分开统计。记录每请求命中/新增 Prefill token、实际状态传输字节、缓存逐出和峰值显存，不假定前缀命中会同比减少跨机传输。若支持不齐则标记未完成公平对照，不能只给单卡或 PD 一方打开缓存，也不能悄悄退化为全量重算。

## 用传输成本约束预期

按已观测的缓存布局，每请求状态量约为：

`B(L) = 49.125 MiB + 0.03125 MiB × 输入 token 数 L`

| 输入 token | 状态量估算 | 有效带宽若为 100 MiB/s，纯搬运约需 |
| --- | --- | --- |
| 128 | 53.125 MiB | 0.53 秒 |
| 512 | 65.125 MiB | 0.65 秒 |
| 2048 | 113.125 MiB | 1.13 秒 |
| 14,336 | 497.125 MiB | 4.97 秒 |

100 MiB/s 是算例，尚非实测，以实际传输耗时为准。

低并发下可先估计 `T_PD ≈ T_prefill(P) + T_transfer + T_decode(D) + T_coordination`。AP-ND 相对 N 单卡要减少 E2E，至少要让节省的 Prefill/等待时间覆盖新增传输和协调开销。
高并发可能重叠不同请求的 P/D，但两阶段和链路中最慢的一项仍限制容量。

14K 每请求约 497 MiB 是从已有短请求布局外推的估算，开跑前需在两方向核对实传字节。它既增加 Prefill 压力，也增加传输压力；本机链路未必因此更有利于 PD。报告应同时解释 Prefill 节省、Decode 干扰减少、传输与接收排队四项，而不是预设长输入必胜。

## 测量、SLO 与断点

- 所有配置通过同一测量入口和同等代理层，固定客户端位置、连接策略、HTTP 并发和超时。记录单卡 A/N 的入口 RTT 差异。PD 只统计 D 侧用户可见响应一次，P 侧首 token 不计为用户 TTFT，不重复计输出吞吐。
- 每请求保存原始 SSE 到达时间、增量 token 计数、usage、错误和结束原因。TTFT 排除 role-only/空 chunk。TPOT 以首末 token 时间和输出数计算；若服务合并多个 token 为一个 chunk，只报 chunk 间隔及平均 TPOT，不把它冒充真实逐 token ITL。
- 按负载分别报告 P50/P90/P95 TTFT、TPOT、E2E，成功输出 token/s、请求/s、SLO 达标率和 goodput。吞吐使用整组从首个提交到最后完成的墙钟时间，另列到达窗口与排空时间。开环 SLO 从计划到达计时，包含发生器等待。
- 没有业务 SLO 时，先用独立低负载 N 单卡校准；对 S、L、C、2048/256 各冻结 `TTFT阈值=max(1秒,2×校准P95)`、`TPOT阈值=1.5×校准P95`，E2E 阈值为 `TTFT阈值+(输出数−1)×TPOT阈值`。请求成功且三项均达标才计 goodput。同一长度所有配置共享阈值，混合轨迹按类别分别判定。明确这是合成 SLO，不是用户体验标准。
- 正式单元至少 50 条、至少 120 秒。按长输入预跑冻结提交预算为 L 7200 秒、C 与 M-code 14400 秒；到达窗口结束后最多排空 120 秒。样本/时长不够则标记不完整，不靠无限延长凑数。闭环是完成至少 50 条，开环是至少到达 50 条，成功率另计。三次重复交错配置顺序，报告每次值、均值与范围；3 次重复不足以支持精细显著性结论，P95 同时标出样本数。
- 14K 预跑后先估算每单元完成 50 条的时间。如果默认截止不足，在正式冻结前按负载统一加预算或声明暂不做该正式单元；不得为凑样本缩短输入。混合组的 50 条不代表每个类别都有 50 条，分位数标明各自样本数，不用少量短请求证明稳定的尾延迟收益。
- 原始请求逐条落盘，完成单元写 summary/checkpoint；配置、输入集、轨迹、代码哈希一起作为恢复键。中断单元保留并重测，不与新单元拼接。只在单元边界接受停止标记；每个配置块完成后检查进度、错误、显存和温度。
- 无进展、OOM、状态校验失败或持续提交滞后时停止该单元，记录证据；不自动调参继续混入同一批。固定运行顺序内每次只跑一种部署，先排空再切换。生产 `.env`/Compose 使用前后哈希核对。

## 执行顺序与交付

先做反向与 14K 正确性验收、32K context/资源/网络校准和测量器，再跑第一组筛选。检查两方向是否都可用、TPOT 是否稳定后，跑两种混合轨迹筛选和会话补测；最后才跑正式矩阵。开环到达压力与服务端可同时驻留数量分开报告。

主矩阵最大规模为筛选 **76 单元**、正式 **78 单元**，不含验收/校准、50 对干扰诊断和必做的 150 条会话请求。仅正式采样窗口下限为 156 分钟，14K 下往往受 50 条样本要求限制，不能据此承诺总耗时。暖缓存会话另加 150 条；M-interference 正式扩展另加 30 单元，均单列预算。加上筛选、重启、预热和排空，分多批进行。

交付一份报告和原始结果索引：两种方向的延迟/吞吐对比、五方案混合负载的 goodput 与尾延迟、传输时间占比、资源峰值及残差。无收益也报告其瓶颈，不能筛掉输给单卡的负载。

 `runs/pd-run`，入口 `run.py --stage all`。`measure.py` 记录 SSE、累计 token、发生器延迟；`report.py` 在单元完成后更新表格与图。`execution.json` 和 `RUNNING.lock` 记录当前单元，原始请求即时落盘，完成单元作为断点。

本批次两卡均使用 `--language-only`、context/token 池 32768、最大运行请求 4、Mamba 槽 8、chunk 256、CPU 权重卸载 0。NVIDIA 静态比例为 0.94，AMD 为 0.90；实际 token 池与状态槽对齐，比例及运行时残差另报。

当前先验收两方向 14K 正确性、并发隔离与 GPU 链路。筛选和正式数据尚未完成，不能据预跑认定 PD 优于单卡。暖前缀组仍属于独立扩展，需先验证异构混合状态缓存支持。


## 发布边界

本计划保留研究设计、测量口径和验收标准。原始请求 SSE、逐传输 trace、压缩轨迹、运行日志、进程锁、重试中间结果和本地部署状态属于实验工作区，不属于发布版；发布版只保留可支撑结论的报告、汇总数据、图表、验证脚本和脱敏部署证据。
